The Challenge

We write the stories first. Product owners aren't ready for that yet.

Traditional user-story generators force clarify → write story → argue about ACs → maybe build a mockup. For Health Cloud, that is the wrong order.

01

Stories before the screen

A Given/When/Then pack is signed before anyone has seen the screen. Refinement becomes an argument about wording, not about what will actually be built.

02

Generic mockups hide cost

A pretty HTML mockup that is not labelled with Salesforce components misleads sizing. OOTB looks the same as a custom LWC until someone has to build it.

03

Same ask, different stack

One person defaults every guided flow to OmniScript. Another defaults to Screen Flow. The build-technology decision was never written down — so it is reinvented every story.

What product owners actually ask first

"What will this look like on-screen — and can we build it with out-of-the-box Lightning, or do we need LWC / Flow / OmniStudio?"

Until those two questions are answered, Given/When/Then is theatre. The team is arguing about acceptance criteria for a shape nobody has agreed to.

The Insight

Show the built feature first. Write the stories after the walkthrough.

A prototype that is grounded in Salesforce components answers both questions in one pass. Stories become a promotion of a signed-off plan — not a substitute for one.

01

See it on-screen

A single-file, clickable HTML mockup, SLDS-flavoured, with happy-path and edge states a product owner can walk through.

02

Know what it costs

Every element is badged with the component that will implement it — OOTB, Config, Flow, LWC, OmniScript, Apex, or an external system.

03

Decide the stack up front

Declarative-first: Lightning + Dynamic Actions and Screen Flow before OmniScript. The rejected alternative is written down, not implied.

A prototype without the grounding is worse than no prototype — it misleads the product owner on cost shape. That is the whole point.

This is not a story generator with a mockup bolted on. It is a Delivery Architect that can stop at the plan, stop at the prototype, or continue to implementation-ready stories — on demand, independently.

The standard that cannot be skipped

Four contracts that stop a bad story from shipping

Must be true
  • Concrete Health Cloud persona — Care Coordinator, Care Manager, Patient Services Rep. Never "user." Patients / Caregivers / Providers are the subject of the work, not the login.
  • Given / When / Then in business language. No Apex class names, SOQL, or API field names inside an AC.
  • Every "records created or updated" outcome carries a Pattern E per-object field spec. Every field. No "etc."
  • Any story that displays, logs, exports, or sends PHI carries a RULE 16 audit AC plus a permission-set / FLS spec.
Will not invent
  • Custom components are verified against the codebase first.
  • Standard Health Cloud objects and fields are verified against the official Salesforce documentation. The bundled catalog is a curated top-list of 94 objects on a Summer '26 / API v67.0 snapshot, not a complete census — so its silence is never evidence that an object or capability does not exist.
  • A missing verification tool is never read as a finding. "I could not confirm it" does not become "so we will build it" — an out-of-the-box-versus-custom call that cannot be verified is raised as a blocking question instead.
  • Unverifiable names are marked proposed — never asserted as existing.
  • OmniScript is not the default. Dynamic Actions, Action Launcher, Screen Flow, and Field Sets are checked first.

# Then, in Cursor:
"Plan and prototype logging a patient call — no stories yet."

There is nothing to install — the skill has no MCP prerequisites. code-review-graph and salesforce-docs are internal to the author's environment and are not publicly distributed: no npm package, no repository, nothing to request. Neither has been available while this skill was built, so the defaults are the normal path — Grep/Glob over your repo for custom components, and the official Health Cloud Object Reference for standard ones, with unverifiable names marked proposed. If you want stronger grounding, configure the official public Salesforce DX MCP Server (npx -y @salesforce/mcp@latest) against an org with Health Cloud deployed.

5 · Why this is a standard, not a demo

Visible on-screen. Honest about cost. Still the architect's call.

Prototype before stories

The product owner walks the screen, then signs the shape. Given/When/Then is a promotion of that plan, not a substitute for it.

Grounded, or not shipped

Every control is labelled with the Salesforce component that will implement it. A generic mockup is treated as a defect.

Declarative-first, documented

The chosen stack and the rejected alternative are both in the plan. OmniStudio is one option. It is never the silent default.

Judgment stays with the team

The skill drafts. The architect confirms personas, PHI/HIPAA (RULE 16), consent, and the build-technology call.
